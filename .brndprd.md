# 1. Product vision and scope

## 1.1 Product objective

Build a web-based trading intelligence platform that allows retail Forex traders and Smart Money Concepts (SMC) analysts to:

1. View interactive financial charts with configurable instruments and timeframes.

2. Capture the current chart and request AI-powered technical analysis in one click.

3. Analyze market structure, liquidity, order blocks, Fair Value Gaps, candlestick patterns, and other technical concepts.

4. Receive structured, explainable analysis with price levels, invalidation conditions, potential targets, and confluence evidence.

5. Save, revisit, compare, and review previous analyses in a personal workspace.

The application must distinguish between what is visibly present on a chart, what is derived from market data, and what is an AI interpretation. This is particularly important when generating price levels or trade scenarios.

## 1.2 MVP definition of done

The MVP is complete when a registered user can sign in, open a chart, select an instrument and timeframe, request analysis, review the structured output, and retrieve the analysis later from their history.

### Core user journey

1. Sign in and open terminal

   User enters the dashboard and loads their default chart workspace.

2. Configure the chart

   Select symbol, timeframe, and chart display settings.

3. Request analysis

   Select a strategy, optionally enter a custom question, and click Snapshot & Analyze.

4. Review AI output

   Inspect bias, supporting evidence, price levels, confluence, and scenario invalidation.

5. Save and revisit

   Open the historical analysis drawer and review saved snapshots and results.

# 4. Charting engine implementation

This is one of the most important technical decisions in the entire project.

## 4.1 TradingView integration strategy

TradingView offers different chart products with different integration permissions. The freely embeddable Advanced Chart widget is not the same as the licensed Advanced Charts library.

The coding agent must first establish which integration is available to the project.

Important integration constraint

Do not assume the free TradingView widget exposes the full TradingView terminal.

The free embeddable widget does not provide unrestricted access to internal chart state, arbitrary drawing tools, or a general-purpose screenshot API. Full drawing capabilities and programmatic chart control depend on the specific TradingView product and licensing terms.

The agent must verify the current TradingView documentation and available account permissions before implementing the chart adapter.

Use the following decision structure:

1. Preferred: TradingView Advanced Charts library, if access and licensing are approved.

   Use its documented chart API and datafeed interface, including drawing capabilities supported by the licensed version.

2. Fallback: TradingView Advanced Chart widget for embedded visualization.

   Use the widget's supported symbol and interval configuration, without claiming access to private chart APIs.

3. Alternative: TradingView Lightweight Charts with a separate permitted market data feed.

   Build custom drawing and chart interaction features where required by the product.

Keep this decision behind a common interface.

TypeScript

```
export interface ChartAdapter {
  mount(container: HTMLElement): Promise<void>;

  setSymbol(symbol: string): Promise<void>;

  setTimeframe(timeframe: string): Promise<void>;

  getVisibleRange(): Promise<{
    from: number;
    to: number;
  } | null>;

  getChartContext(): Promise<ChartContext>;

  captureSnapshot(): Promise<SnapshotResult>;

  destroy(): void;
}
```

The methods that the selected chart provider cannot support must return a documented unsupported result or a controlled error. Never fabricate chart data to satisfy the interface.

## 4.4 Chart snapshot implementation

Implement a snapshot pipeline that:

1. Requests the current visible chart context.

2. Captures a PNG or JPEG through a documented chart export API, where available.

3. Falls back to an application-managed chart capture mechanism only where the provider's terms and browser security restrictions permit it.

4. Associates the snapshot with the active symbol, timeframe, timestamp, strategy, and visible range.

5. Uploads the image to private storage.

6. Submits the image and normalized market context to the backend.

A key technical limitation is cross-origin canvas security. An embedded third-party iframe generally cannot be captured by the parent page as though it were a local canvas. The agent must not implement a fake screenshot using a blank canvas or silently substitute an unrelated image.

If chart image capture is not available under the selected integration, the product should display a clear integration error or use an explicitly designed data-only analysis mode.

# 5. Gemini AI analysis engine

The AI engine is the core intelligence layer of the product. It must do more than send an image to Gemini and display free-form text.

The implementation should use a structured analysis pipeline, with deterministic data validation, strategy-specific instructions, schema-constrained output, and evidence tracking.

## 5.1 Analysis pipeline

1. User initiates analysis

Snapshot, symbol, timeframe, strategy, custom question

2. Validate and normalize

Authentication, request limits, image validation, candle context

3. Prepare analysis context

Image, OHLC candles, timeframe, strategy rules, user prompt

4. Gemini analysis

Visual interpretation and structured technical findings

5. Validate AI response

Zod schema, price consistency, evidence checks, uncertainty handling

6. Persist and return

Save analysis, snapshot, metadata, and normalized result

## 5.2 Strategy engine

Implement each strategy as an independent configuration and prompt module.

TypeScript

```
export type AnalysisStrategy =
  | "smc"
  | "chart_patterns"
  | "candlestick_reversals"
  | "combined";
```

Create a strategy registry:

TypeScript

```
export interface StrategyDefinition {
  id: AnalysisStrategy;
  label: string;
  description: string;
  systemInstructions: string[];

  requiredEvidence: string[];

  supportedTimeframes: string[];
}
```

The registry should be stored in a dedicated module, not scattered throughout UI components.

### Strategy A: Smart Money Concepts (SMC)

The analysis should examine:

- Swing highs and swing lows.

- Higher highs, higher lows, lower highs, and lower lows.

- Break of Structure (BOS).

- Change of Character (CHOCH) or Market Structure Shift (MSS).

- Fair Value Gaps (FVG).

- Order blocks and their mitigation status.

- Liquidity pools above highs and below lows.

- Equal highs and equal lows.

- Buy-side and sell-side liquidity.

- Liquidity sweeps and displacement.

- Premium and discount zones relative to a defined dealing range.

Every finding must include its timeframe, price zone, evidence, and confidence or uncertainty.

An order block should not be classified as valid merely because a candle has an opposing color. The engine should define the structural and displacement criteria used to identify it.

### Strategy B: Traditional chart patterns

Include pattern detection for:

- Double tops and double bottoms.

- Head and shoulders and inverse head and shoulders.

- Triangles: ascending, descending, and symmetrical.

- Flags and pennants.

- Wedges.

- Channels.

- Rectangles and ranges.

For each pattern, capture the relevant boundaries, breakout status, invalidation conditions, and supporting candle structure.

### Strategy C: Candlestick reversals

Analyze recognized reversal patterns such as:

- Bullish and bearish engulfing.

- Hammer and shooting star.

- Morning star and evening star.

- Piercing line and dark cloud cover.

- Doji-based reversal contexts.

A candlestick pattern should be contextualized by its location within market structure. A candle formation alone should not automatically determine the market bias.

### Strategy D: Combined confluence

The combined strategy should evaluate evidence from the other three strategy modules.

The AI should identify:

- Structure and directional context.

- Liquidity and price delivery.

- Chart patterns.

- Candlestick evidence.

- Agreement and disagreement between the findings.

It must not count the same underlying price event multiple times as independent evidence.

## 5.4 Master system prompt

The following is a starting system prompt for the AI coding agent to implement. It should be versioned and refined with real chart examples.

ApexSMC Analysis System Prompt

v1.0

Use as a server-side instruction template. Inject validated chart context and strategy instructions separately.

You are the technical chart analysis engine for ApexSMC, an AI-assisted market analysis platform.

Your task is to interpret the supplied chart image, structured OHLC data, instrument, timeframe, and selected analysis strategy.

Follow these rules:

1. Analyze only the information provided. Never claim access to live market prices, news, order books, or broker data unless that information is explicitly supplied in the request.

2. Distinguish visually observed evidence from derived calculations and AI interpretations.

3. Identify market structure, relevant liquidity, Fair Value Gaps, order blocks, chart patterns, and candlestick formations only when sufficient evidence exists.

4. Never invent exact prices, candle timestamps, or market levels. Use structured OHLC data for exact numerical calculations where available.

5. If the chart is unclear, the instrument cannot be identified, or the evidence is insufficient, return an insufficient-data status.

6. Use the selected strategy as the primary analytical framework. Do not apply unrelated strategy rules unless the combined strategy is selected.

7. Explain the evidence supporting the directional bias and identify conflicting evidence.

8. Treat stop-loss and take-profit values as hypothetical technical scenario levels, not instructions or guarantees.

9. Never guarantee market direction, trading profits, or setup success.

10. Return only a response matching the specified structured output schema.

## 5.5 Structured AI response schema

The AI response must be a typed object, not arbitrary Markdown.

Use Zod to define and validate the response:

TypeScript

```
import { z } from "zod";

const PriceLevelSchema = z.object({
  label: z.string(),
  price: z.number().positive(),
  timeframe: z.string(),
  levelType: z.enum([
    "support",
    "resistance",
    "order_block",
    "fair_value_gap",
    "liquidity",
    "invalidation",
    "target",
    "other"
  ]),
  evidence: z.string(),
  confidence: z.number().min(0).max(100)
});

const AnalysisSchema = z.object({
  status: z.enum([
    "complete",
    "insufficient_data",
    "partial"
  ]),

  bias: z.enum([
    "bullish",
    "bearish",
    "neutral",
    "undetermined"
  ]),

  symbol: z.string(),
  timeframe: z.string(),

  summary: z.string(),

  confluence: z.object({
    score: z.number().min(0).max(100),
    factors: z.array(z.object({
      name: z.string(),
      contribution: z.number(),
      evidence: z.string()
    }))
  }),

  keyLevels: z.array(PriceLevelSchema),

  scenarios: z.array(z.object({
    name: z.string(),
    direction: z.enum(["bullish", "bearish"]),
    trigger: z.string(),
    invalidationPrice: z.number().positive().nullable(),
    targetPrices: z.array(z.number().positive()),
    rationale: z.string()
  })),

  reasoning: z.array(z.object({
    observation: z.string(),
    interpretation: z.string(),
    timeframe: z.string(),
    evidenceSource: z.enum([
      "chart_image",
      "ohlc_data",
      "user_drawing"
    ])
  })),

  limitations: z.array(z.string())
});

export type AnalysisResult = z.infer<
  typeof AnalysisSchema
>;
```

The implementation should additionally enforce cross-field business rules, because a valid JSON schema does not guarantee that the analysis is internally consistent.

For example:

- If `status` is `insufficient_data`, the system must not display a confident actionable scenario.

- If the bias is `undetermined`, the UI must not show a bullish or bearish trade setup as confirmed.

- If the model cannot establish a numerical level, it must return no level rather than invent one.

- If the confluence score is unavailable or invalid, return a null score in an appropriately updated schema instead of fabricating a number.

## 5.6 Confluence scoring

The confluence score must be explicitly defined. Do not allow the AI to produce an unexplained number that appears statistically validated.

For the MVP, use a rule-based evidence score derived from documented criteria, with Gemini supplying evidence and classifications.

An illustrative weighting model:

|
Evidence category

|

Illustrative weight

|
| --- | --- |
|

Higher-timeframe structure

|

25%

|
|

Liquidity and sweep evidence

|

20%

|
|

Order block / FVG alignment

|

20%

|
|

Lower-timeframe confirmation

|

20%

|
|

Candlestick or pattern confirmation

|

15%

|

These weights are starting configuration values, not validated trading-performance weights. Store them in a versioned strategy configuration so they can be adjusted after testing.

A simple normalized score can be calculated as:

S=∑i=1nwiei∑i=1nwiS=\frac{\sum*{i=1}^{n} w_i e_i}{\sum*{i=1}^{n} w_i}S=∑i=1nwi∑i=1nwiei

Where:

- wiw_iwi is the configured weight of an evidence category.

- eie_iei is a validated evidence value between 0 and 1.

- SSS is the normalized score between 0 and 1.

Display the score as a percentage for readability.

The interface should label this as "Technical Confluence" or "Evidence Alignment," not "Probability of Profit" or "Win Rate."

A 78/100 score must never be presented as a 78% probability that a trade will win.

## 7.3 Row-level security

Enable Row Level Security (RLS) on all user-owned tables.

Policies must enforce:

- Users can only read their own analyses.

- Users can only insert analyses associated with their authenticated identity.

- Users cannot change another user's snapshot ownership.

- Users can only delete or modify their own records.

- Private snapshot objects are only accessible to their owner or authorized server processes.

Do not rely exclusively on frontend filtering to isolate user data.

Use Supabase migrations for every schema change. Do not create production tables manually through the dashboard without recording the corresponding migration.

The application handles financial chart data and private user workspaces. Security needs to be designed before implementing the analysis endpoint.

The historical log is not simply a list of previous AI responses. It should become the foundation for future analysis review and backtesting.

- Strategy.

- Timeframe.

- Bias.

- Date range.

Use cursor-based pagination to avoid loading the user's entire history into memory.

## 9.2 Reproducibility requirements

Every saved analysis should retain enough information to understand what the AI saw at the time.

Store:

1. The chart snapshot or a reference to the private stored image.

2. The symbol and timeframe.

3. The snapshot timestamp and chart timezone.

4. The available candle data and visible range.

5. The selected strategy and custom prompt.

6. The model identifier and prompt version.

7. The validated AI result and limitations.

If the original chart provider no longer supports a historical symbol or the market data changes, the saved analysis should still be viewable using the original snapshot.

## 9.3 Backtesting roadmap

For the MVP, implement retrospective review rather than claiming that the system has a validated backtesting engine.

The first review features should allow users to:

- Open an old snapshot.

- View the original AI bias and scenario levels.

- Add manual notes and review outcomes.

- Mark whether a technical level was reached, invalidated, or remained unresolved.

A future backtesting engine will need historical OHLC data, deterministic entry and exit rules, transaction costs, spreads, slippage, and a defined evaluation period.

AI-generated historical chart analysis must not be presented as an unbiased backtest unless the model only uses information that would have been available at the historical decision time. Otherwise, look-ahead bias may invalidate the results.
